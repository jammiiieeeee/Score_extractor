Clean Architecture

A Beginner's Guide Using Real-World Code

What is Clean Architecture?

Clean Architecture is a software design philosophy that separates concerns into concentric layers. The core principle is: dependencies only point inward.

Key Principle: The outer layers depend on inner layers, but the inner layers never depend on outer layers. This makes your code testable, maintainable, and flexible.

The Four Layers (From Outside → Inside)

1. API Layer (Outermost)
Entry points: GUI, CLI, Web endpoints
↓
2. Application Layer
Use Cases: Business operations/workflows
↓
3. Domain Layer (Core)
Business Rules: Models, Interfaces, Value Objects
↑
4. Infrastructure Layer
Implementations: Databases, APIs, External Services

Project Structure

Let's look at how this project implements Clean Architecture:

src/ ├── api/ # API Layer │ └── gui_api.py # PyQt6 GUI entry point ├── application/ # Application Layer │ ├── use_cases.py # Main extraction workflow │ └── extraction_components.py # Helper components ├── domain/ # Domain Layer (Core) │ ├── models.py # Business objects │ ├── interfaces.py # Abstract contracts │ └── deduplication.py # Business logic └── infrastructure/ # Infrastructure Layer ├── video_service.py # OpenCV implementation ├── ocr_service.py # PaddleOCR implementation └── pdf_service.py # ReportLab implementation

Layer 1: Domain Layer (The Heart)

The domain layer contains your core business logic. It has zero dependencies on external frameworks.

# src/domain/models.py from dataclasses import dataclass from typing import Optional import numpy as np @dataclass class Frame: image: np.ndarray timestamp: float index: int path: Optional[str] = None
Why? The Frame model is a pure data structure. It doesn't know about video files, OCR, or PDFs. It just represents what a "frame" is in our business context.

Layer 2: Interfaces (Contracts)

Interfaces define what needs to happen, not how. They live in the domain layer but are implemented in infrastructure.

# src/domain/interfaces.py from abc import ABC, abstractmethod class IVideoService(ABC): @abstractmethod def open_video(self, video_path: str) -> None: pass @abstractmethod def read_frames(self): pass @abstractmethod def close(self) -> None: pass class IOcrService(ABC): @abstractmethod def initialize(self) -> bool: pass @abstractmethod def get_leftmost_number(self, image, vertical_range, ...): pass
Crucial Rule: Interfaces are in the domain layer, but they describe services that the domain needs. The domain doesn't know how these services are implemented!

Layer 3: Application Layer (Orchestration)

Use cases orchestrate the workflow. They use domain objects and interfaces, but don't know about specific implementations.

# src/application/use_cases.py class ExtractScoreUseCase: def __init__( self, video_service: IVideoService, # Interface, not implementation! ocr_service: IOcrService, # Interface, not implementation! file_service: IFileService, config: ScoreConfig ): self.video_service = video_service self.ocr_service = ocr_service self.file_service = file_service self.config = config def execute(self, video_path: str, ...): # The workflow - doesn't know about OpenCV or PaddleOCR! self.video_service.open_video(video_path) # ... extraction logic ... self.video_service.close()
Dependency Injection: The use case receives interfaces (not concrete classes). This means we can swap implementations without changing the business logic!

Layer 4: Infrastructure Layer (Implementations)

Infrastructure contains the actual implementations of interfaces. This is where external libraries live.

# src/infrastructure/video_service.py import cv2 # External library! from src.domain.interfaces import IVideoService class VideoService(IVideoService): def __init__(self): self.cap = None # OpenCV-specific state def open_video(self, video_path: str) -> None: self.cap = cv2.VideoCapture(video_path) # OpenCV implementation if not self.cap.isOpened(): raise ValueError(f"Could not open video: {video_path}") def read_frames(self): while True: ret, frame = self.cap.read() if not ret: break yield frame, timestamp, frame_idx
Isolation: All OpenCV code is in one file. If we wanted to switch to FFmpeg, we'd only change this file—the rest of the system stays the same!

Real Benefits in This Project

1. Testability

We can test business logic without video files or OCR engines:

# Mock the interfaces for testing class MockVideoService(IVideoService): def open_video(self, video_path): pass # Do nothing def read_frames(self): yield mock_frame, 0.0, 0 # Return test data # Now test the use case with fake data! use_case = ExtractScoreUseCase( video_service=MockVideoService(), ocr_service=MockOcrService(), ... )

2. Swappable Components

Need to change OCR engines? Just create a new implementation:

# Current: PaddleOCR from src.infrastructure.ocr_service import OcrService # Future: Tesseract (just change this one line!) from src.infrastructure.tesseract_ocr import TesseractOcrService

3. Clear Boundaries

Everyone knows where to find code:

  • Business rules? → Domain layer
  • New workflow? → Application layer
  • External service? → Infrastructure layer
  • User interface? → API layer

The Dependency Rule

API Layer depends on → Application Layer
↓
Application Layer depends on → Domain Layer
↓
Domain Layer depends on → Nothing (except standard libraries)
↑
Infrastructure Layer implements → Domain Interfaces
Violation Example: If your Domain layer imports OpenCV or PaddleOCR, you've broken the rule! Those belong in Infrastructure.

Summary: Key Takeaways

For Beginners:
  1. Start with the Domain: Define your business objects and rules first
  2. Use Interfaces: Create contracts before implementations
  3. Inject Dependencies: Pass implementations in, don't hardcode them
  4. Keep Outer Layers Thin: They should mostly delegate to inner layers
  5. Test from Inside Out: Domain → Application → Infrastructure → API

This architecture scales from small projects to large systems. The Piano Score Extractor demonstrates Clean Architecture at a manageable size—perfect for learning!
