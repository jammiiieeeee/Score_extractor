Lesson 1: GitHub CI/CD — From Zero to Automated Tests

What you'll learn: How GitHub Actions runs your tests automatically every time you push code.

Tied to your project: Your .github/workflows/test.yml file — we'll break it down line by line.

1. What is CI/CD?

CI = Continuous Integration. CD = Continuous Delivery/Deployment.

Think of it as a robot that:

  1. Watches your GitHub repo
  2. When you push code, it spins up a fresh computer in the cloud
  3. Installs your dependencies
  4. Runs your tests
  5. Tells you if anything broke
You push code → GitHub detects push → Spins up Windows VM
→ Installs Python + deps → Runs pytest → ✅ Pass or ❌ Fail
Why does this matter? Without CI, you only know tests pass on your computer. With CI, you know they pass on a clean machine every time — no "works on my machine" excuses.

2. Anatomy of a GitHub Actions Workflow

Your workflow lives at .github/workflows/test.yml. Let's break it down:

Part A: When does it run?

name: Tests

on:
  push:
    branches: [main, master]
  pull_request:
    branches: [main, master]

This says: "Run tests when someone pushes to main or master, or when a pull request targets those branches."

Key concept: Triggers on: defines when the workflow runs. Common triggers:
  • push — code pushed to a branch
  • pull_request — PR opened/updated
  • schedule — cron job (e.g., daily at 2am)
  • workflow_dispatch — manual button in GitHub UI

Part B: What machine does it run on?

jobs:
  test:
    runs-on: windows-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.12"]

windows-latest means a Windows Server VM. GitHub provides free runners:

  • ubuntu-latest — Linux (fastest, most common)
  • windows-latest — Windows Server
  • macos-latest — macOS

The matrix means: run the entire job twice — once with Python 3.10, once with 3.12. If either fails, the workflow fails.

Part C: What steps does it run?

steps:
  - uses: actions/checkout@v4

  - name: Set up Python ${{ matrix.python-version }}
    uses: actions/setup-python@v5
    with:
      python-version: ${{ matrix.python-version }}

  - name: Install dependencies
    run: |
      python -m pip install --upgrade pip
      python -m pip install -r requirements.txt

  - name: Run fast tests
    run: python -m pytest tests/ -m "not slow" --cov=src --cov-report=xml --timeout=120 -v

Each step does one thing:

StepWhat it doesWhy
checkout@v4Downloads your repoThe VM starts empty — needs your code
setup-python@v5Installs PythonThe VM doesn't have Python by default
pip installInstalls dependenciesYour code needs OpenCV, pytest, etc.
pytestRuns your testsThe whole point!
The ${{ }} syntax This is GitHub Actions' template language. ${{ matrix.python-version }} gets replaced with the current matrix value (e.g., "3.10" or "3.12"). Think of it like f-strings for YAML.

3. Your Workflow — Line by Line

Here's your actual .github/workflows/test.yml with annotations:

name: Tests                    # Name shown in GitHub UI

on:                            # When to trigger
  push:
    branches: [main, master]   # On push to main/master
  pull_request:
    branches: [main, master]   # On PR targeting main/master

jobs:
  test:                        # Job name
    runs-on: windows-latest    # Windows VM (your project is Windows-only)
    strategy:
      matrix:
        python-version: ["3.10", "3.12"]  # Test on both versions

    steps:
      - uses: actions/checkout@v4         # Clone the repo

      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v5     # Install Python
        with:
          python-version: ${{ matrix.python-version }}

      - name: Cache pip packages          # Speed up repeated runs
        uses: actions/cache@v4
        with:
          path: ~\AppData\Local\pip\Cache
          key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}
          restore-keys: ${{ runner.os }}-pip-

      - name: Cache PaddleOCR models      # Don't re-download 500MB models
        uses: actions/cache@v4
        with:
          path: |
            ~\AppData\Roaming\paddleocr
            ~\.paddleocr
          key: ${{ runner.os }}-paddleocr-models

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          python -m pip install -r requirements.txt

      - name: Run fast tests              # Skip @slow tests in CI
        run: python -m pytest tests/ -m "not slow" --cov=src --cov-report=xml --timeout=120 -v

      - name: Upload coverage             # Save test coverage report
        if: matrix.python-version == '3.12'
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage.xml

4. Key Concepts

Caching

- name: Cache pip packages
  uses: actions/cache@v4
  with:
    path: ~\AppData\Local\pip\Cache
    key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}

Without caching, every run downloads all dependencies from scratch (slow!). With caching, GitHub saves the pip folder and reuses it if requirements.txt hasn't changed.

First run: Download 2GB of deps → Save to cache
Second run: Load from cache (10s) → Run tests
After dep change: Download new deps → Update cache

Artifacts

- name: Upload coverage
  uses: actions/upload-artifact@v4
  with:
    name: coverage-report
    path: coverage.xml

Artifacts are files保存ed after a workflow run. You can download them from the GitHub UI — useful for coverage reports, logs, or built binaries.

Conditionals

if: matrix.python-version == '3.12'

This step only runs for Python 3.12 (not 3.10). Avoids uploading duplicate coverage reports.

5. The Test Marker System

Your pytest.ini defines markers:

[pytest]
markers =
    slow: tests requiring real video files or PaddleOCR
    integration: tests needing real filesystem I/O
    unit: pure logic tests with no I/O

In CI, you run -m "not slow" to skip the 9 slow tests (they take ~36s and need a real video). Fast tests run in ~45s.

Local vs CI
  • Local: pytest tests/ — runs everything (370 tests)
  • CI: pytest tests/ -m "not slow" — runs fast subset (361 tests)
